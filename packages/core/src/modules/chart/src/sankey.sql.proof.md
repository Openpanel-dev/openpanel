# sankey.sql.ts — V1 -> V2 result-set proof (M7-004)

Both statements of every sankey mode were executed twice against the same data — once as V1 (the `git HEAD` `packages/db/src/services/sankey.service.ts`, `c4760ac2`, captured by wrapping the shared ClickHouse client) and once as V2 (the fragment the core service sends) — through one `@clickhouse/client` with `format: 'JSON'` and the same `session_timezone`. The two responses were compared on `data` and `meta`. In addition, the two services' full JSON results (nodes + links, after all of the post-processing) were compared for all 12 cases: **12/12 identical**.

- **Date**: 2026-09-04. **Data**: local prod-copy `openpanel` (319,499,000 events, static). Projects: `secure-privacy`, `bayse` (America/New_York).
- **Machine**: single-node ClickHouse on a 4-vCPU box — timings are directional only; production is 2 shards x 2 replicas (`docs/ENVIRONMENT.md`).
- **Cluster note.** The `HAVING session_id IN (SELECT session_id FROM start_event_sessions)` clauses are V1's and are ported **verbatim**: no `IN` was converted to or from `GLOBAL IN`. Whether they should be `GLOBAL IN` on the 2x2 cluster is a pre-existing question this conversion neither answers nor changes (`docs/ENVIRONMENT.md`), and it is recorded as debt in the task report.
- **One case reads IDENTICAL AS SET.** The transitions statement orders by `step ASC, value DESC`, which leaves rows sharing a `(step, value)` pair in arbitrary order. Measured on 2026-09-04: **V1's own statement, executed 4 times unchanged, returned 4 different row orders and one identical row set.** Row order is therefore not part of the contract — the service groups transitions by step and source before using them — so that case is compared as a set, exactly as M7-003 compared the chart statements.

- **Amended by M27-001 (2026-09-15): the dedup expression is no longer V1's.** V1's
  `arrayFilter((x, i) -> i = 1 OR x != events_raw[i - 1], groupArray(event_name) as events_raw, arrayEnumerate(events_raw))`
  is Theta(n^2) in the longest single session's event count and could not answer at a 7-day window on
  a busy project (`docs/ANALYTICS_PERFORMANCE.md` section 6.1). Every `-- V2` statement below now reads
  `arrayCompact(groupArray(event_name))`; the `-- V1` statements are left exactly as V1 wrote them, so the
  two columns differ in that one expression by design. Re-proved against the local prod copy on
  **2026-09-15**, `use_query_condition_cache=0`, `max_memory_usage=6 GiB`, per-query `memory_usage` and
  `elapsed_ns` read off `X-ClickHouse-Summary`:
  - **Result sets:** `cityHash64(arraySort(groupArray(tuple(*))))` compared old vs new on every
    (project, window) pair where the old spelling still survives — `earlysalary-production` 30 d and
    `chatpaper` 30 d, both statements: **identical, 4/4**. One of the four (`earlysalary-production`'s
    transitions statement) also differs in row ORDER between the two spellings — and equally between two
    runs of either spelling, because of the `(step, value)` ties the bullet above already records. It is
    compared as a set for that reason.
  - **Cost, both statements, `mode: 'after'`, 3 steps, 30-day window:** `verdict` FAIL -> 2,931 ms /
    660 MiB · `bayse` FAIL -> 4,606 ms / 1,327 MiB · `earlysalary-production` 10,129 ms -> 5,927 ms /
    1,504 MiB · `website-8103` FAIL (`would use 2.03 PiB`) -> 2,607 ms / 1,035 MiB · `chatpaper`
    13,453 ms -> 12,639 ms / 2,132 MiB. `website-8103` at 1 day: FAIL (`768.88 GiB`) -> 147 ms / 20 MiB.

- **Verdict**: 23 cases, 0 not identical.
